Walmart Lakehouse Pipeline
dbt + Databricks + Airflow

An end-to-end, orchestrated ELT project: raw retail data lands in a Databricks bronze layer, dbt transforms it through silver and gold using the medallion pattern, and Apache Airflow (in Docker) runs the whole thing on a schedule.

Databricks (Delta Lake)dbt Core 1.12dbt-databricks 1.13 Apache Airflow 3.4Docker ComposePython 3.12 · uvJinjaSCD Type 2

1The 60-second pitch

Memorise this. Every other section is the detail behind one of these sentences.

Say this in an interview “I built a retail analytics pipeline on the medallion architecture. Raw Walmart-style data – orders, order items, customers, products, employees and stores – is ingested into a bronze schema in Databricks by a Databricks job that handles change data capture. dbt then builds a silver technical layer with incremental merge models, a silver business layer that joins everything into one big table, and a gold layer with a fact table plus SCD Type 2 dimensions built with dbt snapshots. Airflow, running in Docker, orchestrates all of it: trigger the Databricks ingestion job and wait for it, clean dbt artefacts, check source freshness, then run and test each layer in order.”

What

A daily batch ELT pipeline producing analytics-ready tables: fact_orders and five history-tracking dimensions.

How

SQL + Jinja models in dbt, run against a Databricks SQL warehouse; orchestrated by an Airflow DAG with 10 ordered tasks.

Why it matters

Incremental loads keep cost low, tests protect quality, snapshots preserve history, and orchestration makes it repeatable.

2Architecture

Data flows left to right through three layers. Airflow sits on top and controls the order.

5Environment setup – how it was built

The order in which the project was created, so you can retell it as a story.

  1. Python environment. uv created .venv with Python 3.12. Dependencies in pyproject.toml: dbt-core, dbt-databricks, databricks-sdk, apache-airflow.
  2. dbt project. dbt init walmart_project scaffolded the folders and picked the Databricks adapter.
  3. Connection. profiles.yml holds host, SQL-warehouse http_path, catalog walmart, schema dbt_schema, and a personal access token. dbt debug confirmed “All checks passed”.
  4. IDE tooling. The dbt Power User extension was pointed at the .venv interpreter so it can find dbt.
  5. Models built layer by layer (sources → silver → OBT → gold → snapshots), running dbt run after each step.
  6. Orchestration. The official Airflow docker-compose.yaml was customised; DAG written in dags/orchestrate.py.
  7. Secrets hygiene. Token moved out of code into environment variables; .gitignore protects .env and profiles.yml.

6Bronze: declaring the sources

dbt does not create bronze. It declares it so models can read it safely and lineage is tracked.

models/sources/sources.yml
sources:
  - name: walmart_databricks      # logical name used in source('walmart_databricks', ...)
    database: walmart             # Unity Catalog catalog
    schema: bronze                # actual schema holding the raw tables
    tables:
      - name: customers
      - name: orders
      - name: products
      - name: employees
      - name: order_items
      - name: stores

Why sources? Instead of hard-coding walmart.bronze.orders, models write {{ source('walmart_databricks','orders') }}. dbt then knows bronze is the root of the lineage graph, you can change the schema in one place, and dbt source freshness can monitor it.

Be honest in the interviewThe ingestion itself (CDC into bronze) is a Databricks job created in the Databricks workspace, outside this repository. This project's code triggers it and waits for it. Explain it as “the ingestion layer, which Airflow orchestrates”.

7Silver technical – incremental models

Six near-identical models, one per bronze table. This is the heart of the incremental strategy.

models/Silver_t/orders_t.sql
{{ config(
    materialized='incremental',
    unique_key='order_id'
) }}
select *,
    current_timestamp() as processed_at
from {{ source('walmart_databricks', 'orders') }}

{% if is_incremental() %}
where updated_timestamp > (
    SELECT COALESCE(MAX(updated_timestamp), '1900-01-01') FROM {{ this }}
)
{% endif %}

Line by line

PieceWhat it does
materialized='incremental'Don't rebuild the table each run. First run creates it; later runs only add or update changed rows.
unique_key='order_id'Tells dbt how to match new rows to existing ones. On Databricks this becomes a Delta MERGE INTO … ON order_id = order_id: matched rows are updated, unmatched are inserted. Result: no duplicates.
select *, current_timestamp() as processed_atCopies all bronze columns and adds an audit column: when dbt processed the row.
source(...)Reads from the declared bronze table.
{% if is_incremental() %}True only when the table already exists and the run is not --full-refresh. So the filter is skipped on the first run (full load) and applied afterwards.
where updated_timestamp > (select max(...) from {{ this }})The watermark. {{ this }} is the silver table itself. Only bronze rows newer than the latest row already loaded are read. COALESCE(..., '1900-01-01') protects against an empty table.

8Silver business – the One Big Table (obt_b)

One wide, denormalised table so analysts and gold models don't have to repeat the joins.

models/silver_b/obt_b.sql (shortened)
{% set configs = [
  { "table": "walmart.silver_t.orders_t",
    "columns": """o.order_id, o.store_id, o.order_timestamp, ...
                  o.created_timestamp AS order_created_timestamp, ...""",
    "alias": "o" },
  { "table": "walmart.silver_t.customers_t",
    "columns": """c.customer_id, c.first_name AS customer_first_name, ...""",
    "alias": "c", "join_condition": "o.customer_id = c.customer_id" },
  { "table": "walmart.silver_t.order_items_t", ... "alias": "oi",
    "join_condition": "o.order_id = oi.order_id" },
  { "table": "walmart.silver_t.products_t",    ... "alias": "p",
    "join_condition": "oi.product_id = p.product_id" },
  { "table": "walmart.silver_t.employees_t",   ... "alias": "e",
    "join_condition": "o.store_id = e.store_id" },
  { "table": "walmart.silver_t.stores_t",      ... "alias": "s",
    "join_condition": "o.store_id = s.store_id" }
] %}

SELECT
  {% for config in configs %}
    {{ config['columns'] }}{% if not loop.last %},{% endif %}
  {% endfor %}
FROM
  {% for config in configs %}
    {% if loop.first %}  {{ config['table'] }} AS {{ config['alias'] }}
    {% else %} LEFT JOIN {{ config['table'] }} AS {{ config['alias'] }}
         ON {{ config['join_condition'] }}
    {% endif %}
  {% endfor %}

How it works

  1. Metadata-driven. A Jinja list describes each table: its name, the columns to pick (renamed with prefixes like customer_city vs store_city to avoid clashes), an alias, and how to join it.
  2. Two loops generate the SQL. Loop 1 writes the SELECT list, inserting commas except after the last item. Loop 2 writes FROM + a chain of LEFT JOINs; the first table is the base.
  3. LEFT JOINs from orders. Every order is kept even if a customer or product is missing.
  4. Adding a table = adding one dict, not rewriting SQL.
Know the weak spotJoining employees on store_id multiplies each order row by the number of employees in the store, which inflates sums such as total_amount. Also, obt_b uses hard-coded table names instead of ref(), so dbt cannot see the dependency (Airflow's task order is what protects it). Mention these as known improvements – it shows maturity (see section 15).

9Gold – dimensions (SCD2) and fact

The star schema analysts actually query.

9.1 Ephemeral models: the “staging” step

Five models eph_customers / employees / orders / products / stores each pick one entity's columns out of obt_b with SELECT DISTINCT. They are ephemeral: dbt never creates a table for them; it inlines their SQL as a CTE into whatever references them (the snapshots).

models/gold/ephemeral/eph_customers.sql
SELECT DISTINCT
    customer_id, customer_first_name, customer_last_name, customer_email,
    customer_phone, customer_city, customer_province, customer_country,
    customer_created_timestamp, customer_updated_timestamp, customer_is_active,
    customer_processed_at,
    CURRENT_TIMESTAMP() AS customer_gold_processed_at
FROM {{ ref('obt_b') }}

DISTINCT is needed because obt_b repeats each customer once per order item.

9.2 Snapshots: SCD Type 2 dimensions

snapshots/dim_customers.yml
snapshots:
  - name: dim_customers
    relation: ref('eph_customers')          # what to snapshot
    config:
      schema: gold
      database: walmart
      unique_key: customer_id               # business key

10Schema macro and project configuration

How tables end up in silver_t, silver_b and gold instead of a pile in one schema.

dbt_project.yml (models section)
models:
  walmart_project:
    Silver_t:
      +materialized: table       # default; each silver model overrides it to incremental
      +schema: Silver_t
    silver_b:
      +materialized: table
      +schema: silver_b
    gold:
      +materialized: table
      +schema: gold
      ephemeral:
        +materialized: ephemeral   # nothing is created, SQL is inlined

The problem and the fix

By default dbt names a custom schema <target schema>_<custom schema>. With target schema dbt_schema I got dbt_schema_Silver_t, but I wanted exactly silver_t. dbt lets a project override its built-in macro by defining one with the same name:

macros/custom_schema.sql
{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- set default_schema = target.schema -%}
    {%- if custom_schema_name is none -%}
        {{ default_schema }}                 # no custom schema → use dbt_schema
    {%- else -%}
        {{ custom_schema_name | trim }}      # custom schema → use it as-is
    {%- endif -%}
{%- endmacro %}

Databricks lower-cases schema names, so Silver_t becomes silver_t. The trade-off: dev and prod would now write to the same schema names, so a real setup would separate them by catalog or target.

11Airflow orchestration

One DAG, orchestrate, ten tasks in a straight line. Each task only starts if the previous one succeeded.

dags/orchestrate.py – Task 1: trigger and wait for ingestion
@dag
def orchestrate():

    @task
    def ingest_cdc():
        ws = WorkspaceClient()               # reads DATABRICKS_HOST / DATABRICKS_TOKEN from env
        job_trigger = ws.jobs.run_now(job_id=...)    # start the Databricks job

        while True:                                    # poll every 5 seconds
            job_run = ws.jobs.get_run(job_trigger.run_id)
            if job_run.state.life_cycle_state in [TERMINATED, SKIPPED, INTERNAL_ERROR]:
                if job_run.state.result_state == RunResultState.SUCCESS:
                    break                              # success → continue DAG
                else:
                    raise Exception("Job failed ...")  # fail → DAG stops here
            time.sleep(5)
        return "CDC Ingestion Completed"

Why poll? run_now returns immediately. Without waiting, dbt could start transforming before new data is in bronze. Polling makes ingestion a real dependency. The token is not in the code any more; the SDK reads it from the environment.

Tasks 2–3: shell tasks
@task.bash
def clean_target():
    return "rm -rf /opt/airflow/walmart_project/target && rm -rf /opt/airflow/walmart_project/logs"

@task.bash
def source_freshness():
    return "cd /opt/airflow/walmart_project && dbt source freshness"

clean_target removes stale compiled artefacts (e.g. a manifest.json built on Windows) so every run is clean. source_freshness needs a cd because bash tasks start in a temp directory, not the dbt project.

Tasks 4–10: BashOperators, then the chain
silver_technical = BashOperator(task_id='silver_technical',
    cwd='/opt/airflow/walmart_project', bash_command='dbt run --select silver_t')
... silver_technical_tests  → 'dbt test --select silver_t'
... silver_business         → 'dbt run --select silver_b'
... silver_business_tests   → 'dbt test --select silver_b'
... gold_ephermeral         → 'dbt run --select gold/ephemeral'
... gold_dimensions         → 'dbt snapshot'
... gold_facts              → 'dbt run --select gold/fact'

ingest_cdc() >> clean_target() >> source_freshness() >> silver_technical
  >> silver_technical_tests >> silver_business >> silver_business_tests
  >> gold_ephermeral >> gold_dimensions >> gold_facts

orchestrate_dag = orchestrate()
  • >> means “then”. If any task fails, downstream tasks are marked upstream_failed and do not run.
  • cwd= runs the command inside the dbt project so dbt finds dbt_project.yml and profiles.yml.
  • Tests sit between layers as quality gates: bad silver data never reaches gold.
  • The ordering is why obt_b is safe even without ref(): silver_t is always finished before silver_b starts.

12Docker deployment of Airflow

Why containers, and what each container does.

ComponentJob
api-serverServes the web UI and API at localhost:8080.

Detail worth knowingairflow.cfg says executor = LocalExecutor, but the compose environment variable AIRFLOW__CORE__EXECUTOR: CeleryExecutor overrides it. Environment variables always beat the config file in Airflow.

Secrets (DATABRICKS_HOST, DATABRICKS_TOKEN) live in .env, which Compose passes to every container. _PIP_ADDITIONAL_REQUIREMENTS installs databricks-sdk dbt-databricks at start-up – quick for development, but a custom Dockerfile is the production approach (faster starts, reproducible).

13One full run, end to end

Walk through this when asked “what happens when the pipeline runs?”

  1. Trigger. Someone (or a schedule) triggers the orchestrate DAG. The scheduler queues ingest_cdc.
  2. Ingest. The worker calls the Databricks Jobs API, starts the CDC job, and polls until it finishes. New or changed rows are now in walmart.bronze.*.
  3. Clean. target/ and logs/ are deleted so nothing stale is reused.
  4. Freshness. dbt source freshness checks that bronze is recent (it needs a loaded_at_field in sources.yml to measure anything).
  5. Silver technical. Six incremental models read only rows whose updated_timestamp is newer than what silver already has and MERGE them in. Then dbt test checks keys are not null and unique.
  6. Silver business. obt_b is rebuilt as a table by joining all silver tables.
  7. Gold. Ephemeral models run (nothing is materialised); dbt snapshot compares each dimension to the previous version, closes changed rows and inserts new ones; fact_orders is rebuilt from obt_b.
  8. Done. Analysts query walmart.gold.fact_orders joined to the dim_* tables. Every task's status and logs are visible in the Airflow UI.

14Problems I hit and how I solved them

Real debugging stories – the best interview material. Each one: problem → cause → fix → lesson.

1. dbt could not connect: “Invalid access token” (HTTP 403)

Cause: the token in profiles.yml was wrong or expired. Fix: generate a new personal access token, update the profile, run dbt debug from inside the project folder until “All checks passed”. Lesson: dbt debug first, always – and run dbt from the folder that contains dbt_project.yml.

2. Schema was dbt_schema_Silver_t, I wanted silver_t

Cause: dbt's default generate_schema_name concatenates target schema and custom schema. Fix: override the macro in macros/custom_schema.sql to return the custom schema as-is. Lesson: dbt's built-ins are overridable macros.

3. Incremental run failed: “Syntax error at or near WHERE / updated_timestamp”

Cause: two bugs of the same family. First a second WHERE after an existing one; later an and with no WHERE before it. It only failed on the second run because is_incremental() is false on the first. Fix: a single where updated_timestamp > … in every silver model. Lesson: test incremental logic with a second run, and read the compiled SQL in target/compiled.

4. DELTA_MERGE_UNRESOLVED_EXPRESSION: cannot resolve store_id

Cause: stores_t had earlier been created from a copy-pasted products model, so the existing table had product columns; the merge on store_id found no such column. Fix: dbt run --full-refresh to rebuild with the right schema. Lesson: incremental models keep old structure; schema changes need a full refresh.

5. obt_b failed: table order_items_t not found

Cause: obt_b used hard-coded table names, so dbt did not know it depends on the silver tables and ran it (alphabetically) before they existed. A renamed model had also left a stale orders_items_t table. Fix: ran in the right order via separate Airflow tasks; dropped the stale table. Lesson: use ref() so dbt builds the dependency graph.

6. uv pip install: “Unexpected '', expected '-c', '-e', '-r'…”

Cause: requirements.txt was saved as UTF-16 (PowerShell redirect). Fix: re-save as UTF-8. Lesson: encoding bugs hide in the first byte.

7. Airflow: DAG missing in UI / ModuleNotFoundError: No module named 'databricks'

Cause: the DAG imported the Databricks SDK, but the Airflow container's Python did not have it (my local .venv is a different Python). Earlier, a string with a missing closing quote caused a SyntaxError. Fix: installed databricks-sdk and dbt-databricks in the image via _PIP_ADDITIONAL_REQUIREMENTS; fixed the syntax. Checked with airflow dags list-import-errors. Lesson: a DAG file must import cleanly inside the container.

8. Secrets in code

Cause: the Databricks token was hard-coded in the DAG. Fix: removed it, read from environment variables via .env, git-ignored .env and profiles.yml, revoked and rotated the token. Lesson: secrets belong in environment/secret stores, never in source.

9. Airflow UI “not showing” after restart

Cause: every container pip-installed packages on start, so the API server took minutes to become healthy; the worker also stayed in Created. Fix: waited for health, started the worker with docker compose up -d airflow-worker. Lesson: check docker compose ps and logs before changing code; build a custom image to avoid slow starts.

15Known limitations and what I would improve

Naming weaknesses yourself is a strength in interviews. Say “here is what I'd do next”.

#LimitationImprovement

16Interview Q&A

Short, honest answers grounded in this project. Click to expand.

Walk me through the project.

Use the 60-second pitch in section 1, then offer to go deeper into any layer.

What is the medallion architecture and why use it?

Bronze = raw, silver = cleaned and conformed, gold = business-ready. It separates concerns, lets you reprocess downstream layers from raw data, and gives each audience the right level of trust and structure.

What is an incremental model and how does yours work?

It only processes new or changed rows. Mine filters on updated_timestamp greater than the maximum already in the target, and uses unique_key so dbt issues a Delta MERGE: update existing keys, insert new ones. First run is a full load because is_incremental() is false.

What if a late-arriving record has an older timestamp than the watermark?

It would be missed. Mitigations: a lookback window (e.g. watermark minus a day), a periodic --full-refresh, or using the ingestion timestamp instead of the business timestamp.

What is unique_key for?

It identifies a row so dbt can update instead of duplicate. Without it, an incremental model just appends.

Explain SCD Type 2. How did you implement it?

Keep every historical version of a dimension row with validity dates. I used dbt snapshots with the timestamp strategy on updated_at; dbt maintains dbt_valid_from/dbt_valid_to, and I set dbt_valid_to_current to 9999-12-31 so current rows are easy to filter.

Snapshot strategies: timestamp vs check?

timestamp relies on a reliable updated-at column (I have one). check compares chosen columns and is used when there is no trustworthy timestamp.

Why ephemeral models?

They are reusable SQL fragments compiled into the downstream query as CTEs – no table to store or maintain. Good for light staging steps feeding snapshots. Downside: harder to debug and can't be queried directly.

What is a One Big Table and when is it a bad idea?

A wide denormalised table that removes joins for consumers. It's simple and fast to query but duplicates data and can blur grain – as I saw with the employees join multiplying rows. A star schema is cleaner for BI; that's why gold has a fact and dimensions.

Why generate obt_b with Jinja?

DRY and maintainable: the table list, columns and join conditions are data, and loops generate the SQL. Adding a source is a one-entry change. The cost is readability – I check the compiled SQL in target/compiled.

What's the difference between ref() and source()?

source() points to raw tables dbt doesn't build; ref() points to other dbt models. Both create lineage edges and resolve to the right database/schema.

How do you ensure data quality?

dbt tests (not_null, unique, conditional via where) placed as gates between layers in Airflow, plus source freshness. Planned: relationship tests, tests on gold, and alerts.

Why Airflow and not just dbt Cloud / a cron job?

The pipeline spans more than dbt: it triggers a Databricks ingestion job and must wait for it. Airflow gives dependencies, retries, history, and a UI across all steps.

How does Airflow know when the Databricks job is done?

The task starts the job with the SDK, then polls get_run every 5 seconds until the lifecycle state is terminal, and raises if the result isn't SUCCESS. (A deferrable operator from the Databricks provider would avoid occupying a worker while waiting.)

What does >> do in the DAG?

Sets task dependencies: left task must succeed before the right one starts. A failure marks downstream tasks upstream_failed.

How do you handle secrets?

Not in code: environment variables from a git-ignored .env (SDK reads DATABRICKS_HOST/TOKEN automatically), profiles.yml git-ignored. For production: Airflow Connections or a secrets manager, short-lived/OAuth tokens, and rotation – I rotated a token after it was exposed.

Why did you override generate_schema_name?

To get exact schema names (silver_t) instead of dbt_schema_silver_t. The trade-off is losing dev/prod isolation, so I'd separate environments by catalog.

What would you do to scale this?

Increase dbt threads, make obt_b and the fact incremental, partition/Z-order Delta tables, add retries and alerting, CI with slim builds, and separate environments. Use Databricks Workflows or dbt task for jobs if Airflow isn't needed.

What was the hardest bug?

Pick one from section 14 – the incremental failures are good: they passed the first run and only broke on the second, which taught me to test the incremental path and read compiled SQL.
